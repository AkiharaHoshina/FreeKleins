# 03 · 业务层（`bizserver.py` / `bizserver.exe`，端口 10301）

登录之后的一切（角色、编队、抽卡、关卡、战斗结算、设置）都走**裸 TCP**，
不是 HTTP。协议代号 **CSPKG**。协议工具在 `_re\bizproto.py`。

## 3.1 帧结构

```
帧 = 4 字节大端头 P  +  payload

P = (compress & 7) | ((encrypt & 7) << 4) | (payloadLen << 8)
```

- `compress`：`1` = payload 是 **LZ4 block** 压缩；`0` = 原样
- `encrypt` ：`1` = payload 是 **XXTEA** 密文；`0` = 明文
- `payloadLen`：高 24 位，payload 字节数

**接收侧顺序**：先 LZ4 解压，再 XXTEA 解密（与发送侧严格相反）。

## 3.2 payload 结构（protobuf）

```
CSPKG_nf {
  1: Head  (CSHead)
  2: Body  (bytes)      ← 各命令自己的 protobuf
}
CSHead {
  1: CmdId    (uint32)
  2: SeqId    (uint32)
  3: RetCode  (uint32)
  4: StrCmdId (string)
  6: SecretKey(string)
}
```

**回包规则**：`CmdId = 请求 CmdId + 1`，`SeqId` 原样回填，`RetCode = 0`。

## 3.3 XXTEA 密钥与两个反直觉细节

```
KEY = b"AA9zg1CZMnYLpA5H"
```

来自 **Ma Bingyao 的实现（`include_length` 变体）**，但实测有两个点和教科书版本不一样，
都用真实抓包（`CSLoginReq`）反推验证过，写在 `bizproto.py` 注释里：

1. **长度字在密文末尾，不在开头**（`v[-1]` 是明文长度，`v[:-1]` 是明文词）。
2. **词按小端**读写。

```python
def xxtea_decrypt(data, key=KEY):
    k = _to_uints(key, False)
    v = _to_uints(data, False)
    _xxtea_decrypt_ip(v, k)
    L = v[-1]              # ← 长度字在末尾
    ...
```

#### 关卡为什么必须"全量下发"

客户端把 `StageList` 当成**"已解锁关卡集合" `StageDict`**，`IsLockLevel` / `IsLockChapter`
的实现就是 `StageDict[key] == nil`。

所以只下发"玩家的通关记录"会导致 `StageDict` 为空 → 每章第一关都判"已锁" →
章节列表在第一项就截断 → **主线只剩第 0 章**（这个症状真实出现过）。

正确做法（现在的实现，`playerdata.build_stage_list`）：

```
CSGetStageListRes { 1: StageList[](CSStageScore)   2: LastStage(CSStageBase)   3: ChapterList[](CSStageChapter) }
CSStageChapter    { 1:Type  2:Chapter  3:IsOpen(bool) }
```

- 遍历 `dataconfig_stage_minor`，把**全部关卡**都塞进 `StageList`，`Score` 用存档里的值（没打过就是 0）
- `LastStage` = 第一章第一关（首页"作战"按钮显示的就是它）
- 遍历 `dataconfig_stage_chapter`，**全部章节 `IsOpen = 1`**

#### 战斗胜负的判定

客户端是用 **`FinishData.Score > 0`** 反推 `battleIsWin` 的，不是直接读 `Type`。
所以回包必须：

```python
rb = pb_b(1, pb_v(1, 3 if win == 1 else 0)) + pb_b(2, stageBase) + pb_b(3, CSGameData)
```

失败 / 中途退出给 0 分 → 客户端老老实实停在结算页；胜利才推进。

**保底规则**（官方已停运，概率由本服按用户给定实现，在 `playerdata.draw()`）：

- **限定（UP）池**（`pool_type == 2` 且有 `up_role`）：
  - 70 抽软保底 → 出"当期限定 SSR **或** 任一常驻 SSR"（50/50）
  - 140 抽硬保底 → **必出当期限定 SSR**，然后保底清零
  - **所有限定池共享同一个保底计数**（存档键 `recruit.up_pity`）
- **常驻池**：70 抽保底出常驻 SSR，然后清零（存档键 `recruit.normal_pity`）
- **非保底抽**：基础 SSR 概率 **2%**
- 稀有度取 `dataconfig_role_config.star`，**4 = 最高（SSR）**
- 消耗道具 **75**（抽卡券）

#### 商店的数据结构（客户端视角，**多处硬约束**）

```
CSSHOP      { 1:Type, 2:LabelList[CSShopLabel] }
CSShopLabel { 1:LabelID, 2:ItemList[CSShopItem] }
CSShopItem  { 1:Id 2:Count 3:MaxCount 4:IsDiscount 5:Cost[] 6:DiscountCost[]
              7:RefreshTm 8:RechargePointID 9:CanBuy 10:BuyEndTm 11:IsBought
              12:RechargePointInfo 13:BuyStartTm 14:ShowStartTm 15:ShowEndTm }
```

配置来源：`shop_base`(大类 1~6) → `shop_label`(标签) → `shop_goods`(商品 426 条)。

**四个反汇编挖出来的硬约束**（每一个都踩过）：

1. **`(Type, LabelID)` 必须成对存在于 `dataconfig_shop_label`**
   客户端 `logic_shop` proto#16 做
   `LabelConfig = getConfigDataByTwoID('dataconfig_shop_label','shop_type',Type,'label_id',LabelID)`，
   查不到就是 nil → 之后定时器 `CheckItemRefresh → GetRefreshShopInfo` 每帧访问 `.LabelConfig.goods` **疯狂报错**。
   → `shop_label` 的 `shop_type` 只有 **2~6 和 101~105/201~204**，**没有 1**，
   所以 `shop_base` 的 **type=1（今日声讯）只能发空 LabelList**。

2. **售罄判定 = `MaxCount - Count == 0`**（proto#26）
   `MaxCount == 0` 是"不限购"哨兵，永不售罄。
   → 必须发 **`Count = 0`**；原来发 `Count=1` 时 `count_limit=1` 的商品直接算售罄。
   而且**售罄项会被 `table.remove` 后 append 到列表末尾** → 看起来像"排序乱了"。

3. **`RefreshTm`（字段 7）不填会被当成"需要刷新"**（proto#20 `CheckItemRefresh`，定时器驱动）
   → `RefreshTm - (now - GetTime) >= 0` 才算新鲜。填 0 会让客户端**每秒重发 `1117`**，
   列表被反复重建 → 滚动时表现为"动态排序不正常"。→ 填 **2100 年**。

4. **`shop_goods` 的行主键 ≠ `id` 字段**（行 251 的 `id` 其实是 772），
   而 `shop_label.goods` 里存的是 **`id`** → 必须按 `id` 建索引。

另外排序（proto#25）是客户端自己按本地 `Config.sort_weight → level → id` 排的，**不依赖服务端下发顺序**。

#### 人民币购买：绕过支付 API

离线环境的死结：客户端拿到 `CSBuyCheckRes` 后会调 `sdk_mgr:SdkOrder(shopId, rechargeDate)`，
而 `sdk/sdk_none.lua`（462 字节）**整个是空壳**（所有函数 `RET0`）→ 卡住 → 表现为"点不动"。

**解法（纯服务端，不用改客户端）**：收到 `1124 CSBuyCheckReq{1:RechargePoint}` 后

1. 照常回 `1125 CSBuyCheckRes`
2. **立刻推送 `1126 CSBuySuccessNotify`**，把商品直接发下去

因为客户端处理 `1126` 的函数（`logic_shop` proto#23）**常量表里没有 `ItemList`** ——
它只把这条当"支付成功"信号去刷 UI，**物品必须由服务端发放**。
服务端用 `RechargePoint` 在 `shop_goods` 里反查商品（45 个充值点，**42 个有奖励**；
剩 3 个 `10001/10002/10003` 是纯充值项，金额在未 dump 到的充值点配置表里）。

## 3.5 热重载数据表 `bizdata.json`

`build_reply()` 会先查 `D:\KleinsPatch\_re\bizdata.json`（**按 mtime 热重载**）：

```json
{ "<请求CmdId>": { "body_hex": "08 01 12 ..", "ret": 0, "res_cmd": null } }
```

命中就用它当响应，方便不改代码直接试协议。没命中才走 Python 硬编码分支。
