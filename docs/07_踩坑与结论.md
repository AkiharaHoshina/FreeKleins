# 07 · 踩坑与结论

这里记的是**花了代价才换来的硬结论**，避免以后重新踩。

## 7.1 ★ LuaJIT 比较跳转的语义（最大的一个坑）

### 结论

> **比较类指令（`ISEQN / ISNEN / ISEQP / ISNEP / ISLT / ISGE / ISF / IST / ISNEV / …`）
> 在条件为真时「执行」紧随其后的那条 `JMP`，条件为假时「跳过」它。
> 跳转目标 = `JMP 的下标 + 1 + offset`。**

**这条规则是反直觉的**（一般会以为"比较为真就跳"），而且我一开始判反了。

### 代价

判反之后，我把 `IsLockLevel / IsLockLevelById / IsLockChapter / IsLockChapterAndInTime`
全部强制返回 `false`（`inject_chapter.py`），结果**把每一章都锁上了**：

> 用户反馈："作战能进去，但主线不能用…只显示第0章"

### 怎么定案的

写 `_br.py` / `validate.py`：**用 lupa 自带的 LuaJIT 编译一段已知源码成字节码，
再用 `ljbc.py` 反汇编，源码与反汇编并排对照**——才确认了真实规则。

### 后续处理

`inject_chapter.py --revert` 还原，**改走服务端结构性修复**：
全量下发 375 关 + 全部章节 `IsOpen=true`（见 [03 §关卡](03_业务层_10301_CSPKG.md)）。
问题解决，且不再依赖任何 Lua 补丁。

**教训**：反汇编器的语义必须用"已知输入 → 已知输出"校准过才能信；
不要凭直觉解释字节码。

## 7.2 自己写的探针把游戏搞崩了

探针里写了 `tostring((...))`。**零参数调用时它会抛** `bad argument #1 to 'tostring'`。
在游戏里表现为：

```
LuaException: logic/chapter_ui/logic_chapter: GetAllChapterConfigs
```

从 `view_home_ui` 冒上来，直接**把「作战」按钮点不动了**。

修法：用 `select("#", ...)` 数参数，再逐个安全格式化：

```lua
local function S(v) ... end          -- 安全打印
```

后来这个 tracer 直接禁用/注释掉了。

**教训**：注入进游戏的诊断代码本身必须绝对安全，否则"观测"就是"破坏"。

## 7.3 空响应体 = 客户端超时

实测确认：**空的响应 body** 会把客户端推到 `ENM_STATUS_CLIENT_TIMEOUT` 分支，
弹"网络异常，请稍后重试"。

→ **关键回包必须非空**。至少 `CSLoginRes` 要带内容：

```python
body = pb_v(2, now) + pb_v(3, 1) + pb_v(8, now) + pb_v(10, 0)
```

## 7.4 `GroupIdx` 是 0-based

客户端在 `logic_role_select` 里反汇编出来的是：

```
ReqModifyHeroGroup(uv1 - 1, uv2 - 1, ...)
```

所以 **`GroupIdx` / `SlotIdx` 都是 0-based**（第 1 编队 = 0）。
服务端存档键是 1-based，要显式转换。

**症状**：客户端永远发 `GroupIdx = 0`，服务端却按 1..6 匹配 →
`ChangeQueueMember` 永远匹配不到 →「编队能确定但编不进」。

## 7.5 `TalentList.Step = 0` 会崩在渲染中途

`CSRoleData.TalentList[].Step` 会被客户端拿去查
`dataconfig_talent_cfg(id, level=Step)`，而**那张表的 `level` 从 1 开始**。

给 0 → 查空 → 编队界面 `UpdateRoleItem` 崩在 `TGETS 'skill_type'`。
**因为图标已经画完了才崩**，所以用户看到的是
「名称/品质/等级/命之座全是占位符」这种很有迷惑性的画面。

→ **`Step` 默认给 1**。

## 7.8 槽位制实验的连环崩（已整体放弃）

**起因**：用户发现原版编队是**稠密**的——"我撤掉第 4 个，567 都会前移"，
用户希望改成"留空位"的槽位制。

**结果**：改完之后

- (a) **加/删角色界面不刷新**——我的覆盖丢掉了原实现里 `changeHeroList` 的副作用；
- (b) **多选直接炸**——`view_role_select_base.RemoveRoleIndex: attempt to index field 'item'`
  （选择器的预览列表拿到了 `ID = 0`）。

精修到"只覆盖删除分支 + 从 `RoleIdList` 过滤 0"之后，用户说"我不干了"，要求**全量回退**。

→ `inject_queue_slot.py --revert` 还原了三个文件
（`role_select_manager.lua` 4175B、`logic_queue.lua` 4351B、`logic_queue_data.lua` 4841B），
**已验证与 `_lua_*_pristine.orig` 备份逐字节相同**。

`playerdata.load()` 也改回稠密语义。

**教训**：覆盖一个 UI 函数时，**原实现的所有副作用都要显式保留**，
否则刷新/联动逻辑会静默失效。

## 7.15 批处理脚本必须用 CRLF + GBK 写

`启动服务端.bat` 第一次是用普通文本工具写的，行尾是 **LF**，结果 cmd.exe 直接跑崩：

```
'01' is not recognized as an internal or external command      ← 来自 chcp 65001
'eins' is not recognized as ...                                ← 来自 title Kleins ...
'~dp0_re"' is not recognized as ...                            ← 来自 cd /d "%~dp0_re"
'cho' is not recognized as ...                                 ← 来自 echo
```

**症状特征**：报错内容都是被**截掉开头一截**的片段，而且每行截掉的长度还不一样。

**原因**：`.bat` 必须用 **CRLF**（`\r\n`）行尾。纯 LF 会让 cmd.exe 按块读取时
对不齐行边界，于是命令被切碎。截断长度不固定，正是因为分块边界落在了不同位置。

**修法**：写文件时用 `"\r\n"` 拼接，编码用 **cp936（GBK）**，
并在首行加 `chcp 936 >nul` 让控制台代码页与文件编码一致（中文就能正常显示）。

校验方法：数一下 CR 和 LF 的字节数是否相等。

```powershell
$b = [IO.File]::ReadAllBytes($p)
($b | Where-Object { $_ -eq 13 }).Count   # 应该等于
($b | Where-Object { $_ -eq 10 }).Count
```

## 7.16 端口探测：两个坑

`启动服务端.bat` 最初用 `netstat -ano | findstr /C:":10300 "` 判断端口是否被占，有两个毛病。

### 坑一：没过滤 `LISTENING`，会把连接线误判成占用

netstat 的输出里，`TCP 127.0.0.1:51234  127.0.0.1:10300  ESTABLISHED` 这种行
**右边**也含 `:10300 `。所以只要有一个残留连接，就会被判成"端口被占用"。

→ 必须加一层 `findstr LISTENING`：

```
netstat -ano | findstr LISTENING | findstr /C:":10300 " >nul 2>&1
```

### 坑二：判断出"被占"之后**照样 `start` 一对新的**

旧的 exe 绑定失败立刻退出，用户只看到两句"旧服务端还开着？"——既吓人又没信息量。

→ 改成**两个端口各判各的**：哪个没起就起哪个，已经在跑的直接 `[跳过]`。
语义从"警告"变成"报告我实际做了什么"。

### 坑三：固定 `timeout /t 3` 等不够

PyInstaller **单文件** exe 每次运行都要先把 ~9.5MB 解包到临时目录，首次常常要 3-8 秒。
固定等 3 秒会导致自检误报 `[X] 没起来`（实际上过一会儿就起来了）。

→ 改成**轮询**：每秒查一次，最多等 20 秒，就绪即打印 `[OK]`。

> 另外，`timeout` 在 stdin 被重定向时会直接报
> `ERROR: Input redirection is not supported`，
> 所以脚本里改用 `ping -n 2 127.0.0.1 >nul` 当 sleep —— 这个在哪都能用。

## 7.17 ★ 换装"要点两次"：典型的"异步数据 vs 同步刷新"竞态

### 症状

点一次「更换着装」，提示音响了但状态不变；再点一次才生效。

### 先排除服务端（重要）

| 怀疑点 | 验证 | 结论 |
|---|---|---|
| 客户端发的请求值不对 | `skin_spy.log` | ❌ 第一次发的就是正确值 |
| 服务端没应用/没落盘 | `bizserver.log` + `player.json` | ❌ 第一次就 `skin=X (ok=True)` 并落盘 |
| `CSRoleData.SkinId` 字段号错 | `pbdesc.py` 重建 | ❌ 就是**字段 17** |
| 回包该带字段 | `pbdesc.py` | ❌ `CSSetRoleSkinRes` 是**空消息** |

**所以"换装本身"第一次就已经成功了，滞后的只是界面按钮。**

### 真正的根因

```
view_role_skin_base.UpdateSkinState(roleId, skinId)
    └─ logic_role_skin.GetSkinState(roleId, skinId)      ← proto#15
           └─ logic_role_data.GetRoleDataById(roleId).RoleSkin   ← 拿服务端角色数据
                 与传入的 skinId 比较:
                     相同 -> 'HaveAndUse'     ("已使用")
                     不同 -> 'HaveAndNotUse'  ("更换着装")
```

`RoleSkin` 来自 **1010 `CSGetRoleListRes`**，是**异步**的。而
`SetRoleSkinRes` 一回来界面就**同步**刷一次 —— 那一刻数据还是旧的 → 算出 `HaveAndNotUse`。
等 1010 回包、数据变新之后，**已经没有任何东西再触发一次刷新了** → 只能靠第二次点击。

### 修法

在 `logic_role.GetRoleListRes`（1010 的回包处理）**之后**重调一次
`view_role_skin_base.UpdateSkinState(roleId, skinId)`。三个文件见 [05 ⑪⑫⑬](05_客户端Lua覆盖清单.md)。

### 踩过的两个弯（都是"看日志才看出来"）

1. **`UpdateSkinState` 没有 self**。
   调用形状是 `(roleId, skinId)` 两个参数。第一版包装把它当方法写成
   `function(self, skinId, ...)` 并把 `self` 存成"界面实例"，结果存进去的是 **角色 ID（1004）**，
   调用时报 `attempt to index upvalue '' (a number value)`。
   → 判据：把第一个参数的类型打进日志，看到 `self=1004` 就真相大白了。

2. **事件总线补发"报成功但送不到"**。
   照抄引擎的 `Notifier:dispatchCmd(cmdName.ROLE_SKIN_UPDATE)`，
   返回 `ok=true`，**但事后日志里没有任何 `UpdateSkinState`** —— 说明界面根本没收到。
   → 教训：**"调用没报错"不等于"效果发生了"**。必须看后续有没有产生预期的副作用日志。

   最后改成绕开总线，直接调 `view.UpdateSkinState(roleId, skinId)`，一次成功。

### 通用教训

**服务端异步回来的数据 + 客户端同步触发的刷新 = 竞态。**
修法不是"多刷一次"，而是**把刷新挪到数据真正到达之后**。
定位这类问题的顺序：先证明数据是对的（排除服务端）→ 找到"谁在什么时候读这份数据"
（反汇编到具体函数）→ 再看"数据到达时有没有人刷新"。
